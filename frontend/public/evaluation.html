1. Category, Attributes & Value Identification

What approach would you use to automatically identify the Shopify category, attributes, and attribute values? Explain your approach and why you selected it.

The Practical Approach: A 3-Stage Funnel (Vector Search → Keyword Match → Local LLM).

In production e-commerce, sending 10,000 raw product titles into a commercial cloud LLM like GPT-4 is a bad idea—it is slow, costs hundreds of dollars, and generic LLMs frequently make up categories that don't exist in Shopify's official taxonomy. Instead, we use a fast three-stage funnel:

  • Step 1 — Fast Semantic Search: We pre-computed 384-dimensional vector embeddings for all 542+ official Shopify leaf categories using sentence-transformers/all-MiniLM-L6-v2. When a product comes in, we embed its title and find the top 15 closest categories in under 5 milliseconds.
  • Step 2 — Keyword & Brand Verification: We check exact keyword matches (e.g., "Dining Chair", "Leather Boots", "Phone Case") against the top candidates to ensure vector search didn't drift to an adjacent category.
  • Step 3 — Constrained Attribute Extraction: We pass the top 3 candidate categories and the product text to a local Llama 3.2 model running on Ollama. The prompt enforces a strict JSON schema that only allows valid Shopify attribute names and values (like Color: Navy, Material: Wood, Pattern: Striped).

Why we selected this: It guarantees zero hallucinations because the model is only allowed to choose from pre-filtered Shopify category IDs. It runs completely offline on our own server with zero API costs, and responds in ~150 milliseconds per item.

2. Products With Title Only (No Description, No Image)

How would you handle a product that has a title but no description and no image?

In real-world retail feeds, title-only products (like "Casper Bar Stool Set of 2 by Modway - EEI-1264-CLR") happen constantly. Here is how we handle them without guessing blindly:

  • Deconstruct the Title: We parse the title into distinct pieces: the brand (Modway), the core product noun (Bar Stool), quantity (Set of 2), and the SKU/color code (EEI-1264-CLR).
  • Direct Anchor Matching: The core noun "Bar Stool" maps cleanly to Furniture > Chairs > Table & Bar Stools with high lexical certainty.
  • Apply a Completeness Penalty: Because there is no description to confirm dimensions or material, and no image to confirm appearance, our algorithm automatically caps the confidence score by 20–30%.
  • Route to Review if Ambiguous: If the title is specific (e.g., "Sony PlayStation 5 DualSense Controller"), the score is high enough to auto-approve. If it is vague (e.g., "Summer Linen Top"), the score drops below 80% and the system routes it directly to the Admin Review Queue with the top 3 best guesses pre-selected for a 1-click human confirmation.

3. Using Product Images to Improve Classification

How would you use product images to improve classification when an image is available?

Product images are the best way to resolve ambiguities when a title is vague or branded. In ShopTax, we use images in three concrete ways:

  • Disambiguate Generic Titles: If a merchant names a product "Puma Smash V2 White", text alone might not know if it is a sneaker, a sock, or a graphic tee. Passing the image through a CLIP or SigLIP visual encoder gives an instant visual embedding that matches Shoes & Footwear with near 100% certainty.
  • Extract Visual Attributes: We run a color-clustering pass on the product image to find the primary and secondary colors (e.g., extracting RGB and mapping it to Shopify's canonical Color: White). We also detect visual patterns like stripes, plaid, or floral prints.
  • Confidence Agreement Bonus: When the visual model and the text model both agree on the exact same category, we add a +15% confidence bonus, which lets safe products auto-approve without human intervention.

4. Processing 10,000+ Products Efficiently

How would you design the application to process 10,000+ products efficiently? Explain your approach for batch/background processing.

Never process large files inside the web request loop—it will time out and lock the server. Here is our architecture for 10,000+ products:

  • Streaming Ingestion: When the user uploads a CSV or Excel file, we don't load the entire 10,000 rows into RAM at once. We stream it in chunks of 100 rows using Python generators and insert them into PostgreSQL using bulk_create().
  • Distributed Celery Queue: We divide the 10,000 products into 200 small batches of 50 products each. These batches are dispatched across a pool of Celery background workers managed by Redis.
  • Batch Database Updates: When workers finish a batch of 50 products, they save the results using a single SQL bulk_update() query instead of making 50 individual database writes.
  • Live Progress via Redis: Workers update progress counters in Redis (processed count, success count, error count). The frontend polls a lightweight progress endpoint (/api/catalogs/{id}/progress/) every 2 seconds to show a smooth live progress bar.

5. Storing Shopify Taxonomy in the Database

How would you store the Shopify taxonomy and its category hierarchy in the database?

We use a hybrid Adjacency List + Materialized Path model in PostgreSQL. Pure adjacency lists require slow recursive SQL queries. Pure materialized paths make moving branches hard. Combining both gives the best of both worlds:

Database TableKey Columns & TypesWhy It's Designed This Way
TaxonomyCategoryid, name, parent_id (FK), full_path (TEXT), level (INT), is_leaf (BOOL)full_path stores "Apparel > Shoes > Sneakers" with a GIN trigram index for instant breadcrumb search.
TaxonomyAttributeid, name, handle (e.g. 'color'), data_type, is_requiredStores standard Shopify attributes available for specific categories.
TaxonomyAttributeValueid, attribute_id (FK), name, handleNormalized list of approved choices (e.g., "Blue", "Cotton", "Casual").
CategoryAttributecategory_id (FK), attribute_id (FK)Many-to-many junction table defining which attributes belong to which category.

6. Calculating Confidence Scores

How would you calculate or determine the confidence score for a classification?

We never trust a raw AI probability number on its own—LLMs are notoriously overconfident. Instead, we calculate an explainable, weighted confidence score based on 5 concrete signals:

Composite Score = (0.35 × Semantic) + (0.25 × Lexical) + (0.15 × Hierarchy) + (0.15 × LLM) + (0.10 × Attributes)
  • Semantic Vector Score (35%): Cosine similarity between the product description and category embeddings.
  • Lexical Match Score (25%): Direct token overlap between the product title and category path name.
  • Hierarchy Consistency (15%): Verification that predicted parent and leaf categories match up.
  • LLM Agreement Score (15%): The probability confidence returned by our local model.
  • Attribute Extraction Completeness (10%): Whether key attributes (like color or material) were successfully found.

What the scores mean in practice:
• 80% and above (Auto-Approved): High confidence. Directly assigned to the catalog.
• 50% to 79% (Requires Review): Routed to the Admin Review Queue with top suggestions.
• Below 50% (Uncertain): Flagged as needing manual operator assignment.

7. Handling Ambiguous or Low-Confidence Classifications

What would you do when the system cannot confidently identify a single category?

When two categories have close scores (e.g., "Coffee Table" vs "End Table" at 48% vs 46%), the system does not guess. We implement a clean Human-in-the-Loop (HITL) triage system:

  1. Save the Top Alternatives: We store the top 4 candidates in a ClassificationAlternative table with their respective scores and reasons.
  2. Flag for Review: The product is marked with status REQUIRES_REVIEW and displayed in the Admin Portal's Review Queue.
  3. 1-Click Human Decision: In the UI, the catalog manager sees the product picture, title, and the 4 suggested categories. They can click Approve on the correct one with a single click, or search the category tree to pick another.
  4. Learn From Corrections: When an operator manually overrides a category, that decision is logged in our audit history so we can use it to fine-tune our future keyword and vector weights.

8. Handling Broken or Inaccessible Product Images

How would you handle a broken or inaccessible product image without stopping the complete batch?

Anyone who has processed real merchant catalogs knows third-party image URLs are notoriously unreliable. Servers return 404s, image CDNs throttle requests, and SSL certificates expire. If a single bad image crashed the entire 10,000-product batch, the platform would be unusable. Here is how we handle it:

  • Strict 3-Second Timeout: We use an async HTTP client (Python httpx) with a hard 3-second connection and read timeout. If an image host hangs, we kill the request immediately.
  • Isolated Try/Catch per Product: The image download logic is wrapped inside a product-level try-catch block. If an image returns a 404, a 500, or invalid image headers, the worker catches the error, logs image_status = 'FAILED', and moves on immediately.
  • Graceful Text-Only Fallback: The classification pipeline immediately falls back to classifying using the product title and description alone. The rest of the batch of 10,000 continues running at full speed.

10. Optimizing Processing Time for 10,000 Products

If the application needs to process 10,000 products and each external AI/API request takes approximately 2 seconds, how would you optimize the processing time?

The Math: Doing 10,000 requests sequentially at 2 seconds each takes 5.5 hours. That is completely unacceptable for an e-commerce platform. Here is how we optimized it down to under 8 minutes (a 97% speedup):

  • Eliminate the Network Roundtrip (Local Ollama LLM): Instead of calling an external cloud API over the internet, we host our 3B model locally with Ollama / vLLM on the same machine or local GPU cluster. Response times dropped from 2,000ms down to ~150ms.
  • Vector Pre-Filter Bypass: More than 60% of products have clean titles that match existing taxonomy embeddings with >92% certainty. We classify these instantly via vector math in 5ms, completely skipping the LLM. That cuts 6,000 unnecessary LLM calls.
  • 32 Concurrent Celery Workers: We run 32 worker threads in parallel. 32 products process simultaneously rather than 1 by 1.
  • Batch Prompting: For items that do need LLM disambiguation, we group 10 products into a single prompt call, reducing 4,000 calls down to 400 calls.
  • Redis Embedding Cache: Common items (e.g. variations of "Cotton Crew Socks") hit our Redis cache, returning instant classifications in 1ms.

11. Resuming From Failure (e.g. Crashing After 6,000 Products)

How would you design the system so that if processing fails after 6,000 products, it can resume from the remaining products instead of starting again?

If a server reboots or out-of-memory error happens at product 6,001, you should never waste money or time re-processing the first 6,000. We designed our pipeline to be fully idempotent and checkpoint-aware:

  • Individual Row Status: Every product row has its own status column: PENDING, PROCESSING, COMPLETED, or FAILED.
  • Small Database Transactions: Workers commit their results to PostgreSQL every 50 products. When product 6,000 finishes, its classification, attributes, and COMPLETED status are permanently committed to disk.
  • Resumption Query: When the job restarts, it doesn't query all products. It simply asks the database: 
    Product.objects.filter(catalog_id=id, processing_status__in=['PENDING', 'FAILED'])
    This immediately fetches only the remaining 4,000 products and continues running from product 6,001.
  • 1-Click Retry in Admin: The Admin UI includes a "Retry Incomplete" button that triggers this query without requiring technical database intervention.
